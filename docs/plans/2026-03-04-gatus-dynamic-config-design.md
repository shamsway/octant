# Gatus Dynamic Config Generation - Design

**Date:** 2026-03-04
**Branch:** `feature/app-migration`
**Status:** Draft

## Goal

Generate Gatus's `config.yaml` endpoints from Nomad service health check definitions, so every service with a Consul health check automatically appears on the Gatus status page without manual YAML maintenance.

## Context

Gatus (`terraform/gatus/`) monitors 11 endpoints across 3 groups, but the lab now runs 38 Nomad jobs with 29 HTTP and 11 TCP health checks registered in Consul. The static `config.yaml` hasn't been updated since initial deployment — 29 services with health checks have no Gatus monitoring.

Every Nomad service already declares a health check (type, path, interval, port) that flows into Consul. This is exactly the data Gatus needs to construct its endpoint config. The script can query the Nomad API, extract check definitions and port/address info, and render a complete Gatus config.

### Current Coverage Gap

| Source | Count |
|--------|-------|
| Services with HTTP health checks | 29 |
| Services with TCP health checks | 11 |
| Total checkable services | 40 |
| Gatus endpoints configured | 11 |
| **Missing** | **29** |

### Current `config.yaml` Structure

```yaml
metrics: true
ui:
  title: Octant
  description: Service health checks
storage:
  type: sqlite
  path: /data/gatus.db
endpoints:
  - name: grafana
    group: monitoring
    url: http://grafana.service.consul:3000/api/health
    interval: 60s
    conditions:
      - "[STATUS] == 200"
```

The pattern is straightforward: each endpoint has a `name`, `group`, `url` (using Consul DNS `<svc>.service.consul:<port><path>`), `interval`, and `conditions`. The current config hardcodes all of this.

## Architecture

```
Nomad Job Specs (.nomad.hcl)
  └── service block: check type, path, port, interval
  └── service block: tags (including homepage.group from companion PRD)
          │
          ▼
    Nomad API (/v1/job/<id>)
      - Service name, port label, check definition
      - Network ports (static or dynamic → resolve via Consul)
          │
          ▼
    Python script (generate-gatus-config.py)
      - Queries all running jobs for service + check definitions
      - Resolves port numbers (static from job spec, dynamic from Consul DNS)
      - Constructs URL: http://<svc>.service.consul:<port><path>
      - Groups endpoints using homepage.group tags (shared with Homepage PRD)
      - Merges with static preamble (metrics, ui, storage, alerting)
      - Renders config.yaml
          │
          ▼
    terraform/gatus/config.yaml (committed to repo)
      → embedded into Nomad job via template stanza
      → Gatus reads at /config/config.yaml inside container
```

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Data source | Nomad API (health checks) | Every service already declares checks — no new tags needed. The data exists, we just need to read it. |
| Grouping source | `homepage.group` tags | Reuse the same grouping from the Homepage PRD. One tag set, two consumers. Services without `homepage.group` get grouped as "other". |
| URL construction | Consul DNS (`<svc>.service.consul:<port>`) | Gatus runs inside the cluster with Consul DNS. This is how the current config works and is the most reliable addressing. |
| Port resolution | Static ports from job spec; Consul DNS for dynamic | Static ports (grafana:3000, loki:3100, etc.) are in the job spec. Dynamic ports resolve via Consul DNS automatically when using the service name. |
| TCP endpoints | Include for databases/protocols | Gatus supports `tcp://` endpoints with `[CONNECTED] == true`. Gives visibility into postgres, redis, mariadb, mongodb, nats availability. |
| Config output | Committed file, not runtime-generated | `config.yaml` is embedded into the Nomad job via `template` stanza from `data.local_file`. Generating at deploy time (not runtime) keeps the config auditable and diffable. |
| Alerting config | Static, hand-maintained section | Alerting rules (Slack, ntfy, etc.) are editorial decisions, not derivable from service metadata. Keep them in a static preamble. |
| Script relationship to Homepage script | Separate script, shared tag reading | Could be a mode of the same script, but separate scripts are simpler and independently runnable. Both parse `homepage.group` from tags. |

## What Gets Changed

| Component | Current State | Target State | Notes |
|-----------|--------------|--------------|-------|
| `terraform/gatus/config.yaml` | 11 hand-maintained endpoints | ~40 generated endpoints | Generated by script, committed |
| `scripts/generate-gatus-config.py` | Does not exist | New script | Queries Nomad API, writes YAML |
| `terraform/*/nomad.hcl` | (no new changes needed) | Same | Health checks already exist; `homepage.group` tags added by companion PRD |

**Key insight**: This PRD requires **no new tags** on services. All the data needed (check type, path, port, interval) is already declared in every Nomad job's `check {}` block. The only reused tag is `homepage.group` for grouping, which comes from the companion Homepage PRD.

## Section 1: Endpoint Generation Rules

### HTTP Endpoints

For each Nomad service with a `type = "http"` check:

```yaml
- name: <service_name>
  group: <homepage.group tag, lowercase, or "other">
  url: http://<service_name>.service.consul:<port><check_path>
  interval: <check_interval, minimum 60s>
  conditions:
    - "[STATUS] == 200"
```

**Port resolution:**
- If the service port is static (e.g., grafana on 3000), use that port number
- If the service port is dynamic, Consul DNS resolves `<svc>.service.consul` to the allocated host:port — use the container's `to` port since Gatus connects via Consul DNS which resolves to the host port

**Interval floor:** Nomad checks run as frequently as every 10s. Gatus doesn't need to poll that aggressively. Use `max(check_interval, 60s)` as the Gatus interval.

### TCP Endpoints

For each Nomad service with a `type = "tcp"` check:

```yaml
- name: <service_name>
  group: <homepage.group tag, lowercase, or "other">
  url: tcp://<service_name>.service.consul:<port>
  interval: 60s
  conditions:
    - "[CONNECTED] == true"
```

### Endpoint Name Mapping

Some Nomad service names differ from what you'd want on a status page:

| Nomad Service Name | Gatus Display Name | Notes |
|---|---|---|
| `web` | `nginx` | Nginx service is registered as `web` |
| `falkordb-ui` | `falkordb-ui` | Keep as-is, separate from `falkordb` TCP |
| `neo4j-ui` | `neo4j-ui` | Keep as-is, separate from `neo4j` TCP |
| `nats-monitoring` | `nats-http` | Monitoring endpoint for NATS |
| `traefik-admin` | `traefik` | Primary Traefik health endpoint |
| `traefik-http` | skip | Covered by traefik-admin |
| `traefik-metrics` | skip | Metrics endpoint, not a health check |

The script should support a name override map for these cases.

### Group Mapping

Groups come from `homepage.group` tags (lowercase). Mapping to the current Gatus convention:

| `homepage.group` Tag | Gatus Group |
|---|---|
| Infrastructure | infrastructure |
| Monitoring | monitoring |
| Observability | monitoring (merge) |
| Databases | databases |
| Apps | apps |
| AI & LLM | ai |
| (no tag) | other |

The group merge (Observability → monitoring) keeps the Gatus page simpler. This is configurable in the script.

### Services to Exclude

| Service | Reason |
|---------|--------|
| `gatus` | Self-referential |
| `homepage` | Not useful to monitor from Gatus (low criticality) |
| `traefik-http` | Redundant with `traefik-admin` |
| `traefik-metrics` | Metrics scrape endpoint, not health |

The script should support an exclusion list.

## Section 2: Generated Config Structure

### Static Preamble (preserved across generations)

```yaml
metrics: true

ui:
  title: Octant
  description: Service health checks

storage:
  type: sqlite
  path: /data/gatus.db

#   ntfy:
#     url: https://ntfy.lab.shamsway.net

```

### Generated Endpoints Section

The script writes the `endpoints:` list, grouped and sorted:

```yaml
endpoints:
  # infrastructure
  - name: traefik
    group: infrastructure
    url: http://traefik-admin.service.consul:9002/ping
    interval: 60s
    conditions:
      - "[STATUS] == 200"

  - name: nginx
    group: infrastructure
    url: http://web.service.consul:8080/
    interval: 60s
    conditions:
      - "[STATUS] == 200"

  # monitoring
  - name: grafana
    group: monitoring
    url: http://grafana.service.consul:3000/api/health
    interval: 60s
    conditions:
      - "[STATUS] == 200"

  # ... etc

  # databases (TCP)
  - name: postgres
    group: databases
    url: tcp://postgres.service.consul:5432
    interval: 60s
    conditions:
      - "[CONNECTED] == true"

  - name: redis
    group: databases
    url: tcp://redis.service.consul:6379
    interval: 60s
    conditions:
      - "[CONNECTED] == true"
```

## Section 3: Python Generator Script

### Location

`scripts/generate-gatus-config.py`

### Behavior

1. **Query Nomad API** — list all running jobs, inspect each for services and checks
2. **Extract check definitions** — type (http/tcp), path, interval, port label
3. **Resolve ports** — map port labels to `to` port numbers from network stanza
4. **Read `homepage.group` tags** — from service tags for grouping
5. **Apply overrides** — name mapping, exclusions, group merges
6. **Merge with static preamble** — metrics, ui, storage, alerting sections
7. **Write `config.yaml`** — to the output path

### CLI Interface

```
usage: generate-gatus-config.py [-h] [--nomad-addr URL] [--output FILE] [--dry-run] [--preamble FILE]

Options:
  --nomad-addr URL     Nomad API address (default: http://localhost:4646)
  --output FILE        Output file (default: terraform/gatus/config.yaml)
  --preamble FILE      Static preamble YAML to prepend (default: built-in)
  --dry-run            Print generated YAML to stdout, don't write files
```

### Configuration (in-script constants or config file)

```python
# Services to exclude from monitoring
EXCLUDE_SERVICES = {"gatus", "homepage", "traefik-http", "traefik-metrics"}

# Service name overrides for display
NAME_OVERRIDES = {
    "web": "nginx",
    "traefik-admin": "traefik",
}

# Group merges (homepage.group → gatus group)
GROUP_MAP = {
    "Infrastructure": "infrastructure",
    "Monitoring": "monitoring",
    "Observability": "monitoring",
    "Databases": "databases",
    "Apps": "apps",
    "AI & LLM": "ai",
}

# Minimum interval (don't poll more frequently than this)
MIN_INTERVAL_SECONDS = 60
```

### Dependencies

- Python 3 stdlib: `urllib.request`, `json`, `argparse`, `collections`
- `PyYAML` — for YAML output

## Section 4: Beyond Consul Health Checks

The MVP generates endpoints from Nomad-registered health checks. Future enhancements could add:

### External Endpoint Monitoring

Gatus can monitor external URLs that aren't part of the Nomad cluster. These would remain in a static section or a separate overrides file:

| Endpoint | Type | URL | Purpose |
|----------|------|-----|---------|
| Consul API | HTTP | `http://consul.service.consul:8500/v1/status/leader` | Consul cluster health |
| Nomad API | HTTP | `http://nomad.service.consul:4646/v1/status/leader` | Nomad cluster health |
| CephFS | ICMP | `icmp://192.168.122.101` | Storage node reachability |
| DNS resolution | DNS | `dns://192.168.122.101` | Consul DNS functioning |

These are infrastructure components that don't run as Nomad jobs but should be monitored. The current config already has `consul` and `nomad` endpoints.

### TLS Certificate Monitoring

For services behind Traefik with `certresolver=cloudflare`, Gatus can check certificate expiry:

```yaml
- name: "lab.shamsway.net TLS"
  url: https://grafana.lab.shamsway.net
  interval: 1h
  conditions:
    - "[CERTIFICATE_EXPIRATION] > 720h"  # 30 days
```

This would be a separate generated section for all services with Traefik HTTPS routing.

### DNS Resolution Checks

Verify Consul DNS is resolving service names correctly:

```yaml
- name: "consul-dns-grafana"
  group: dns
  url: "192.168.122.101"
  dns:
    query-name: "grafana.service.consul"
    query-type: "A"
  conditions:
    - "[DNS_RCODE] == NOERROR"
```

### Response Time Thresholds

Add `[RESPONSE_TIME] < 5000` conditions to HTTP endpoints to catch slow services before they fail:

```yaml
conditions:
  - "[STATUS] == 200"
  - "[RESPONSE_TIME] < 5000"
```

### Recommendation

**MVP: Nomad health checks only.** The script generates HTTP and TCP endpoints from existing Nomad service definitions. This alone takes coverage from 11 to ~38 endpoints with zero new configuration on services.

**Phase 2:** Add a static overrides file for external endpoints (Consul, Nomad, CephFS) and TLS certificate checks. These can be merged by the script from a separate `gatus-overrides.yaml` file.

## Non-Goals

- **Alerting configuration**: Alert routing (ntfy, Slack, PagerDuty) is an operational decision. The script preserves whatever alerting config is in the preamble but doesn't generate it.
- **Uptime Kuma replacement**: Uptime Kuma serves a different purpose (external monitoring, public status page). Gatus monitors internal service health via Consul DNS.
- **Runtime config reload**: Gatus watches its config file for changes, but since the config is embedded via Nomad `template`, changing it requires a Gatus redeployment anyway. Generate → commit → `terraform apply` is the workflow.
- **Widget integration with Homepage**: Homepage supports a Gatus widget for inline status. That's a separate concern from config generation.

## Validation

1. **Dry-run comparison**: `python3 scripts/generate-gatus-config.py --dry-run` should produce output that is a superset of the current `config.yaml` (all 11 existing endpoints should still appear, plus ~29 new ones)
2. **YAML validity**: Generated config should parse cleanly with `python3 -c "import yaml; yaml.safe_load(open('config.yaml'))"`
3. **Deploy and verify**: After `terraform apply` for gatus, check `gatus.lab.shamsway.net` — all groups should appear with green/red status indicators
4. **Spot-check URLs**: Verify a sample of generated Consul DNS URLs resolve correctly: `dig grafana.service.consul @192.168.122.101`
5. **TCP endpoint test**: Confirm TCP endpoints (postgres, redis, mariadb) show as connected on the Gatus dashboard

## Relationship to Homepage PRD

Both PRDs share the `homepage.group` tag as a grouping mechanism. The recommended implementation order:

1. **Homepage PRD first** — adds `homepage.*` tags to all services (including `homepage.group`)
2. **Gatus PRD second** — consumes `homepage.group` for grouping, plus reads existing health check data

The Gatus script can run independently even without `homepage.group` tags — services without the tag simply get grouped as "other". But implementing the Homepage tags first gives clean grouping from the start.
